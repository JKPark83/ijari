Phase 5 — 전국 확장과 용량 게이트

서울에서 검증된 파이프라인을 전국 17개 시도로 넓히고, 무료 티어로 버틸 수 있는지 숫자로 결정한다

선행: Phase 4 MVP 완성 · 예상 2~3일 · 다음: Phase 6 출시 + 자동화

결정 변경 (2026-08-08) — 서울만 적재해도 무료 티어(500MB) 중 258MB를 썼고, 전국은 DB 용량이 약 1.2GB로 추정돼 무료 티어를 초과한다. 그래서 §2의 용량 게이트(450MB 기준 무료/Pro 결정)는 폐기하고, 로컬 self-host 전환(OrbStack self-host, 비용 0원)으로 대체한다. 이 phase를 시작하기 전에 로컬 DB 스택 구축(아래 0절)이 선행 단계로 추가됐다. 배경은 플랜 개요 2절 참고.

✅ 완료 판정

  1. 전국 17개 시도가 적재되고 검증 쿼리(Phase 2의 10종)가 전국 기준으로 통과한다.
  2. DB 용량 실측값과 티어 결정(무료 유지 또는 Pro 전환)이 docs/capacity.md에 기록돼 있다.
  3. 앱에서 서울 밖(부산·제주 등) 아무 곳이나 줌인해도 자리·연대기가 정상으로 보인다.
  4. RPC 3종의 explain analyze 결과가 인덱스를 타고, 실기기 체감 로딩이 서울과 다르지 않다.

0. 로컬 DB 스택 구축 — 선행 단계 (결정 변경 2026-08-08)

전국 확장을 시작하기 전에, 클라우드 Pro 대신 로컬 self-host 스택을 먼저 구성한다. Supabase 클라우드(서울 데이터)는 당분간 MVP 검증용으로 유지하고, 전국 데이터는 새 로컬 스택에 적재한다.

  • 컨테이너 스택 — OrbStack(Docker) 위에 PostGIS Postgres + PostgREST + nginx 프록시(/rest/v1 경로를 PostgREST로 매핑) 3개 컨테이너. compose 구성은 저장소 infra/local/에 둔다.
  • 저장 위치 — DB 데이터는 외장 드라이브 T31에 둔다. T31이 ExFAT 포맷이라 Postgres 데이터 디렉터리를 직접 둘 수 없어, T31 안에 APFS 스파스 이미지(ijari-db.sparsebundle)를 만들어 마운트하고 그 안에 데이터 디렉터리를 둔다. 원본 CSV(약 20GB)는 이미지가 필요 없어 ExFAT에 직접 저장한다(/Volumes/T31/ijari/data).
  • 앱 전환 — supabase-swift 코드 구조는 그대로 두고 Config의 URL·anon key만 로컬 스택 주소로 교체한다(PostgREST API 표면이 Supabase와 동일해 RPC 3종·RLS 정책은 그대로 재사용). 단 Mac의 LAN IP로 접속하므로 같은 네트워크에서만 동작하고, http 평문 통신이라 iOS ATS(App Transport Security) 예외 설정이 필요하다.

로컬 스택은 외부에서 접근할 수 없다 — 개발 Mac과 같은 네트워크에 있는 기기에서만 앱이 동작한다. App Store 공개 배포 시점의 백엔드 재검토 과제는 Phase 6에 남겨둔다.

1. 확장 시나리오 — 코드 변경은 거의 없어야 정상

Phase 2 파이프라인이 시도별 CSV를 순회하는 구조였다면, 이 phase의 작업은 사실상 데이터 내려받기와 실행 시간이다. 코드 수정이 자꾸 필요하다면 서울 특화 가정(주소 파싱 등)이 숨어 있다는 신호이므로 그 가정부터 제거한다.

  1. 나머지 16개 시도 × 14개 분기 CSV를 data/raw/{분기}/에 추가로 받는다. 전국 1분기가 약 1.36GB이므로 총 20GB 안팎의 디스크가 필요하다 — 받기 전에 여유 확인.
  2. run.py --sido all로 전체 파이프라인 실행. DuckDB 처리 시간은 분 단위로 늘어날 뿐 병목이 아니다. 병목은 COPY 적재(수백만 행) — 진행 로그를 넣어 몇 분 걸리는지 기록한다.
  3. 적재 후 app_meta.coverage를 서울 → 전국으로 갱신 (앱 하단 문구가 자동으로 바뀐다).

지역별 파일 분할 방식이 분기마다 다를 수 있다(시도별 zip / 전국 단일 / 파일명 표기 차이). normalize 단계에서 파일명이 아니라 데이터 안의 시도 코드 컬럼을 기준으로 처리하면 분할 방식과 무관해진다.

2. 용량 게이트 — D5의 결정 지점 (참고용, 로컬 전환으로 대체됨)

이 절은 Supabase 클라우드를 계속 쓴다는 전제로 짠 원래 게이트 로직이다. 결정 변경(2026-08-08)으로 실제 운영은 로컬 self-host 전환으로 대체됐고, 아래 내용은 판단 배경을 남기기 위한 참고용이다.

select pg_size_pretty(pg_database_size(current_database()));
-- 테이블별 상세
select relname, pg_size_pretty(pg_total_relation_size(relid))
from pg_catalog.pg_statio_user_tables order by pg_total_relation_size(relid) desc;

게이트 기준: 전국 적재 후 DB 총 용량이 450MB를 넘으면 Pro($25/월) 전환을 결정한다. 500MB 한도에 50MB 여유를 두는 이유는 분기 갱신 시 truncate + COPY 과정에서 옛 행이 vacuum되기 전까지 일시적으로 더 차지하기 때문이다. 450MB 미만이면 무료 유지, 넘으면 그 자리에서 Pro 전환하거나 커버리지를 수도권+광역시로 줄이는 대안과 비교해 결정한다. 결정과 근거를 docs/capacity.md에 남긴다.

실측 전 추정(전국 자리 150만~180만 + 이력, PostGIS 인덱스 포함 400~700MB)은 경계에 걸쳐 있다 — 그래서 이 게이트는 추정이 아니라 실측으로 정한다. 용량이 넘칠 때 시도해볼 다이어트(순서대로):

  1. place_history에서 category_name 제거하고 코드→이름 매핑 테이블 분리 (수백만 행 × 한글 문자열이 가장 비싸다)
  2. 교체 0회·단일 이력 자리의 history 행 생략 (places만으로 표현 가능)
  3. road_address 정규화(시도·시군구 접두어 제거 후 앱에서 조합)

3. 성능 점검

서버 쪽

  • RPC 3종을 전국 데이터 기준으로 explain (analyze, buffers). map_places가 GiST 인덱스(places_geom_idx)를 타는지 확인 — Seq Scan이 보이면 bbox 조건이 인덱스를 못 쓰는 형태로 변형된 것.
  • Supabase는 API 경유 쿼리에 statement timeout을 걸어둔다(대시보드에서 롤별 확인 가능). 느린 쿼리는 그냥 에러가 되므로, 타임아웃 한도를 늘리기보다 쿼리를 그 안에 들어오게 만드는 것이 원칙.
  • 넓은 bbox + places 레벨 조합(이론상 수만 행)은 앱 줌 사다리가 막아주지만, RPC 자체도 limit 1000 상한이 있어 이중으로 안전한지 재확인.

앱 쪽

  • 서울 밖 사용자 시나리오: 첫 화면을 서울 고정이 아니라 전국 뷰(sido 레벨)로 시작하거나, 위치 권한이 있으면 내 주변으로. 첫 화면 정책을 이 phase에서 확정한다.
  • 메모리 캐시 히트율을 로그로 확인 — 같은 bbox 재방문 시 요청이 안 나가는지.
  • 지도 드래그 왕복 테스트(서울 ↔ 부산)에서 마커 수천 개가 쌓여 프레임이 떨어지지 않는지 — 레벨 전환 시 이전 마커 배열을 확실히 버린다.

4. 데이터 품질 — 서울 밖에서 새로 생기는 문제

  • 시도별 건강 체크(Phase 1의 health 측정)를 전국으로 확대해 시도별 층정보 결측률 표를 만든다. 특정 시도가 유난히 나쁘면(예: 결측 80%) 그 시도의 confidence 정책을 따로 볼 근거가 된다.
  • 세종시가 특이 사례였는지도 이때 판명된다 — 기획서의 수치(ID 유지율 등)와 전국 수치를 비교해 docs/capacity.md에 같이 기록.
  • 좌표가 시도 경계를 크게 벗어나는 행(오입력)은 버리고 카운트를 로그로 남긴다.
