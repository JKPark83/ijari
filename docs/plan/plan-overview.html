2026-08-07 작성 · phase 상세는 개별 문서로 분리 · 진행 체크는 tasks.md

세 줄 요약

  • 백엔드는 Supabase Postgres + PostGIS. 앱이 supabase-swift로 직접 질의하고, 쓰기는 로컬 ETL만 한다. 기획 원안의 "SQLite 조각 정적 배포"는 폐기했다.
  • phase는 7개(0~6). 각 phase가 끝나면 반드시 눈으로 보거나 직접 실행해서 확인할 수 있는 산출물이 나온다.
  • Phase 1의 "아는 자리 20곳 중 15곳 일치" 게이트를 통과하지 못하면 이후 phase는 진행하지 않는다.

1. 확정 결정 기록

플랜을 짜기 전에 확정한 결정들이다. 이후 phase 문서는 전부 이 표를 전제로 쓴다.

#결정선택근거
D1백엔드 구조Supabase Postgres 직접 질의앱이 supabase-swift로 화면 영역을 바로 질의. 항상 최신 데이터, 앱 로직 최소. 로컬 DB(GRDB)와 SQLite 배포는 쓰지 않는다.
D2줌아웃 집계사전 집계 테이블ETL에서 시도·시군구·행정동 통계를 미리 계산해 region_stats로 적재. 실시간 GROUP BY보다 빠르고 비용 예측이 쉽다.
D3ETL 실행로컬 수동, 자동화는 Phase 6분기 1회라 노트북 실행으로 충분하고 결과를 눈으로 검증할 수 있다. GitHub Actions는 마지막에 붙인다.
D4오프라인온라인 전용MVP는 네트워크 필수. 조회 결과만 메모리 캐시. 오프라인은 후속 과제로만 기록.
D5적재 범위무료 티어 + 서울 먼저서울(추정 100~150MB)로 Phase 4까지 완주하고, Phase 5에서 실측 용량을 보고 Pro($25/월) 전환을 결정한다.
D6iOS 구성iOS 17+ / XcodeGenTeslaSync와 같은 방식 — project.yml로 생성, .xcodeproj는 커밋하지 않음. supabase-swift v2, MapKit SwiftUI.
D7보안 경계anon key + 읽기 전용 RLSanon key는 앱에 넣어도 되는 공개 키다. 모든 테이블에 RLS를 켜고 select 정책만 준다. 쓰기는 로컬 ETL의 service_role 키로만.
D8분기 갱신 방식단일 트랜잭션 truncate + COPYPostgres MVCC 덕에 트랜잭션이 커밋되기 전까지 앱은 이전 데이터를 그대로 본다. 별도 스테이징 스왑 없이도 원자적 교체가 된다.
D9다점포 층 처리자리 = 건물관리번호#층 유지, 교체 수는 min(소멸, 신규)호정보가 100% 결측이라 층보다 잘게 못 나눈다. 한 층에 점포가 여럿이면 상세 화면 문구를 "이 층 점포 N곳 · 교체 M번"으로 바꿔 정직하게 표현한다. Phase 1 게이트에서 이 규칙이 체감상 맞는지 함께 검증한다.
D10식별자 표기DB·코드는 영어 snake_casePostgres·Swift에서 한글 식별자는 고통이다. 주석만 한국어.

2. 아키텍처

핵심은 역할 분리다. 무거운 계산(분기 대조·교체 판정·집계)은 전부 로컬 ETL이 미리 끝내고, Supabase에는 완성된 결과만 들어간다. 앱은 그 결과를 읽기만 한다. 그래서 서버에서 도는 커스텀 코드가 없고, 분기 갱신은 ETL을 다시 돌리는 것으로 끝난다.

3. 데이터 스키마

테이블은 4개다. 전체 DDL·인덱스·RLS·RPC 원문은 Phase 2 문서에 있다.

앱이 호출하는 진입점은 테이블이 아니라 RPC 함수 3개다. 테이블 구조가 바뀌어도 함수 시그니처만 지키면 앱은 깨지지 않는다.

RPC입력출력쓰는 곳
map_regions레벨(sido/sigungu/dong) + 화면 bboxregion_stats 행들줌아웃 지도 마커
map_places화면 bbox + 상한(기본 500행)places 행들 (교체 많은 순)줌인 지도 개별 자리
place_detailplace_key자리 + 연대기 + 동네 평균 (JSON)상세 바텀 시트

4. Phase 지도

모든 phase는 "완료를 눈으로 확인하는 방법"이 정의돼 있고, 그 확인을 통과해야 다음으로 간다.

Phase문서내용눈으로 확인하는 방법예상
0준비Supabase 프로젝트·Python 환경·저장소·데이터 확보SQL Editor에서 PostGIS 버전 출력, CSV 행 수 출력0.5~1일
1데이터 스파이크서울 2개 분기 대조 → 검증 리포트 생성게이트: 아는 자리 20곳 중 15곳 일치. 실패 시 프로젝트 중단2~3일
2스키마 + ETLDDL·RLS·RPC 생성, 서울 14개 분기 전체 적재Supabase Studio 검증 쿼리 10종 + curl로 RPC 호출3~4일
3지도 골격XcodeGen 프로젝트, 3단계 줌 사다리 지도실기기에서 서울 지도 탐색, 교체 횟수별 색 확인3~4일
4연대기 상세자리 탭 → 바텀 시트 타임라인실기기에서 자리를 눌러 "주인이 N번 바뀌었습니다" 확인2~3일
5전국 확장나머지 16개 시도 적재, 용량·성능 게이트전국 아무 곳이나 탐색 + DB 용량·응답 속도 실측치2~3일
6출시 + 자동화출처 표시·심사 대응·App Store 제출, GHA 분기 갱신TestFlight 설치, GHA 수동 실행 성공3~4일

순서를 건너뛰지 않는다. 특히 Phase 1 게이트 전에 iOS 코드를 먼저 쓰고 싶어지는 유혹을 경계해야 한다 — 데이터가 틀렸으면 앱은 의미가 없다.

5. 저장소 구조

새 저장소 하나(모노레포)로 간다. 이름 가칭 ijari, 앱 가칭 "이 자리", 번들 ID 가칭 com.jkpark.ijari.

ijari/
├── pipeline/               # Python ETL (Phase 1~2, 5)
│   ├── pyproject.toml      # uv 관리: duckdb, psycopg[binary], python-dotenv
│   ├── download.py         # 분기 CSV 확보 (URL 매핑 + 수동 폴백)
│   ├── normalize.py        # 컬럼 표준화 · 자리 키 · 상호 정규화
│   ├── timeline.py         # 점포 수명 연결 · ID 재발급 병합 · 교체 판정
│   ├── aggregate.py        # places · region_stats 계산
│   ├── load.py             # Supabase COPY 적재 (단일 트랜잭션)
│   ├── verify.py           # 적재 후 검증 쿼리 일괄 실행
│   └── run.py              # 전체 실행 CLI: python run.py --quarters 2023Q1..최신 --sido 서울
├── supabase/
│   ├── schema.sql          # DDL + 인덱스 (Phase 2)
│   ├── policies.sql        # RLS
│   └── functions.sql       # RPC 3종
├── ios/
│   ├── project.yml         # XcodeGen — .xcodeproj는 커밋 안 함
│   └── Ijari/              # 앱 소스 (Phase 3~4)
├── data/                   # .gitignore — raw CSV, 분기별 보관
│   └── raw/2023Q1/…
└── docs/                   # 이 플랜 문서의 사본 또는 링크
